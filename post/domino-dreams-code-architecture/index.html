Domino Dreams 代码架构深度研究报告

2026-11-20 • 40 分钟阅读 • 游戏设计 · 行业观察

一句话结论：Domino Dreams 把 24,673 个类摊成了一座按业务分区的城市——逻辑全在包内，协议是明文 JSON，运营活动是画出来的图，上线新活动不用发版。 本文继上次 Monopoly Go 与 Royal Kingdom 的拆解之后，这次拆的是 SuperPlay 自己的包，看一家头部休闲游戏公司怎么搭长线运营的架构底座。

📖 文中 type[N]/m[N]/文件行号是反编译清单的坐标（相当于页码），只作证据用，已全部下沉到各节末尾的折叠证据块，读白话可完全跳过。

0. 一段话读懂

Domino Dreams 是 SuperPlay（Screenshake 原名，与 Dice Dreams 同厂；SuperPlay.Domino.* 命名空间 4745 处命中，grep 实测）的多米诺休闲手游，拆解版本 1.64.1.0，拿到的是逻辑全在包内的 IL2CPP 产物（编译后包内仍附带全量类名/方法名清单，即 metadata——这正是静态拆解能进行的原因）。

把这个包想象成一座规划良好的城市：代码按业务分区（变现区、集卡区、玩法区、社交区），区与区之间不串门、只通过「接口邮局」递协议书；对外有六条专线（六条 WebSocket 长连接，各连一个微服务）；活动内容由总部（服务端）传真过来（配置下发），不用重印城市地图（客户端发版）。整座城市 24,673 幢建筑（类型）、149,003 条管线（方法），全部类名方法名可读——这正是本次拆解能进行的原因。

五个核心结论，正文逐条给证据：

  1. 分层是按业务域切分的，不是按技术层：Domino.Game 2752 / Domino.MTX 927 / Domino.Messages 755 / Domino.Domino 717 / Domino.TemplatesBehavior 887，每个程序集对应一个可独立演进的 LiveOps 业务域（§二）。
  2. 网络栈是全自研：SuperHTTP 程序集（29 类型）自带 HTTP 客户端、WebSocket、证书 pin 三件套；六个 WebSocket 服务各挂一个 SocketComponent，共享一个 51 方法的基类（§三）。
  3. 协议层是明文 JSON：wire 格式 [{"Id":N,"Error":0,"Messages":[{"Item1":"类型名","Item2":payload}]}]，无序列化混淆——对逆向者友好，对开发效率友好（§四）。
  4. LiveOps 内容管线是四通道配置 + 可视化行为图：DCX/LCX/MTX/PCX 四族配置（CDN + WS delta 同步），887 类型的 TemplatesBehavior 里藏着一整套 BlueGraph 节点图运行时——运营活动是画出来的，不是写出来的（§六）。
  5. 与前作 Dice Dreams 相比完成了一次网络架构换代：Dice Dreams 走 REST HTTPS API + MessagePack 变体 WS；Domino Dreams 六服务全 WebSocket + 明文 JSON，配置同步也从 REST hash 增量搬进 WS 消息（§八）。

一、一条消息的旅行（主线）

从玩家一次点击看整座城市怎么协作：

玩家点击 → [Domino.Domino 本地规则引擎跑一帧] → [Domino.Game 状态机打包消息]
→ [SocketComponent 六专线之一] → 明文 JSON → wss:// 六微服务 → 服务端记账/回包
→ [Domino.Game 解包分发] → [Domino.Templates 模板演出] → 玩家看到结果

白话拆解每一站：

  • 本地先跑：出牌、匹配、结算全在客户端本地引擎算完（手感零延迟）。

  • 打包：Domino.Game 的状态机把「发生了什么」装进一条消息——消息格式是明文 JSON，类型名即文档（§四）。

  • 发车：六个 SocketComponent 组件各守一条专线，共享同一个基类（登录/收发/休眠/风控全套 51 方法），各自只填自己的业务差异（§三）。

  • 记账：服务端收到后记账、回包；涉及花钱的走 DTC 专线对账（§七 安全姿态）。

  • 演出：回包由 UI 模板组件演出，行为图（BlueGraph）决定演什么——运营活动就是画出来的图（§六）。

分区之间的三条「城市规划决策」：

  • Contracts 是纯接口层：121 个类型几乎全是端口定义。业务域之间不直接引用，通过 Contracts 里的接口 + 依赖注入拼装——这是六边形架构（六边形架构 = 模块之间只通过「协议书」式的接口对话，谁也不直接调用谁的内部，模块可独立替换）。

  • 规则核与表现彻底分离：桌面玩法（717 类型）与骰子棋盘副玩法（185 类型，全部为棋盘事件命名空间）互不依赖，靠元游戏编排。SuperPlay 把 Dice Dreams 的棋盘玩法做成了可插拔事件模块。

  • 客户端自带 outcome 模拟器：33 个类型的模拟器家族（基础/发现优先/概率/空/旧核五个模拟器）。在客户端跑概率模拟——用于动画预演、教学对局或概率展示，具体用途尚无法从包内确认，但「模拟器是一等公民」这件事本身说明他们的数值验证是工程化的。

三、自研网络栈：SuperHTTP + SocketComponent 家族

3.1 SuperHTTP：29 个类型的全自研传输栈

SuperHTTP.dll 不是对 UnityWebRequest 的封装，是一套完整自研实现：HTTP 客户端（带异步状态机，还内嵌了一层 Mono 风格兼容层）、WebSocket（极简实现，方法集只有开/关/发/收/释放，帧解析自管）、证书 pin 三件套（接口 + 默认实现 + pin 处理器）。

这套栈选型的含义：Unity 自带网络组件的证书校验链不好做 pin 注入，自研栈让 pin 逻辑完全在自己手里。代价是重造轮子，收益是传输层 100% 可控。

证据（SuperHTTP 坐标）

  • 规模：29 类型（来源: assemblies.txt:99）

  • HTTP 客户端：SuperHTTP.HTTPRequest（type[23670]）+ SuperHTTP.HTTPResponse（type[23671]），async 状态机（<GetAsync>d__5 / <GetAsyncWithProgress>d__7 / <PostAsync>d__8 / <PutDataAsync>d__2，来源: dump_structures.txt:77594 节），内嵌 Mono 风格 WebRequest/WebResponse/WebHeaderCollection 兼容层（type[9961]/[9962]/[9956]）

  • WebSocket：SuperHTTP.WebSocket.WebSocket（type[23679]），方法集 Open / Close / Send / ReceiveLoop / Dispose + HeaderParser/HeaderInfoTable（来源: dump_structures.txt:77679-77690 附近，m[146390]-m[146400]）

  • 证书 pin：ISSLCertificateValidationService（type[23672]）+ SSLCertificateValidationService（type[23673]）+ SSLPinningCertificateHandler（type[23674]）（来源: dump_structures.txt:77669-77676）

3.3 SocketComponent：六服务共享的连接基类

客户端为每个 WS 服务写了一个 socket 组件（socket 组件 = 维持一条与服务器的长连接并负责收发消息的代码件），全部继承同一个基类——六条连接共用同一套登录/收发/休眠代码，各自只填自己的差异部分。基类 51 个方法构成完整的连接生命周期，白话读法：

  • 登录流：判断要不要登录 → 生成登录消息 → 执行登录 → 处理登录响应

  • 收发流：发请求 → 收消息 → 解包（请求响应与主动推送分开处理）

  • 批处理：批次号分配 → 批次消息组 → 发送批次

  • 生命周期：开连接 → 处理循环 → 后台休眠（App 切后台挂起省电，回前台唤醒）

  • 风控侧：封禁判定、封禁原因、未成年判定

  • 可观测：连接状态、平均响应时间

子类只做差异化的三件事：各自的登录消息（GS 带全量身份字段）、各自的业务方法（DTC 挂四个交易方法，GS 挂存档/补偿/集卡交易）。

3.4 请求-响应-推送三模型

每个发出的请求挂一个「等待回包」对象（可取消/完成/失败/中止），请求带 Id 匹配响应；服务端主动推送走独立队列——wire 格式里的 "Id" 字段就是为这个服务的。连接有休眠协议：App 切后台挂起 socket 省电。

证据（三模型坐标）

  • PendingSocketRequest（type[558]，方法 Cancel/Resolve/Fail/Abort）+ PendingSocketResponse（type[556]）+ PendingSocketPushMessage（type[557]）+ 泛型 TypedPendingSocketRequest<T>（type[559]）（来源: dump_structures.txt:23022-23032）

  • 休眠：SetHibernationState + BackendComponentHibernationStateRequest（type[18819]@47471）

四、协议层：明文 JSON、契约共享、bot 在契约层

4.1 wire 格式

真机 TX 抓包确认，协议没有二进制混淆，消息类型名即文档：

[{"Id":1,"Error":0,"Messages":[{"Item1":"SPSF.GS.Common.Messages.GetCompensationsRequestMessage","Item2":null}]}]

C# 元组序列化风格（Item1/Item2）直接暴露在 wire 上——服务端用的就是 Newtonsoft.Json 序列化整个消息信封。五个服务各有一条登录消息（Race 的登录帧未在本批 TX 捕获中出现），登录链为：五服务并发登录 → GS 补偿/身份查询 → 全量拉状态 → DTC IAP 对账。

证据（wire 与登录链坐标）

  • wire 格式来源：protocol-message-inventory.json:4

  • 五条登录消息：GSLoginRequestMessage / DTC_LoginRequestMessage / GCXLoginRequestMessage / SocialLoginRequestMessage / SPSF_TournamentsLoginRequestMessage（Race 未捕获，来源: protocol-message-inventory.json:11-30）

  • 登录链：五服务并发登录（Id=0）→ GS 补偿/身份查询 → GetGameStateRequestMessage 全量拉状态 → DTC GetUnconsumedTransactionsRequestMessage IAP 对账（来源: protocol-message-inventory.json:31-46）

4.3 Bot 在契约层存在

四个「玩家画像」契约并列定义在 Domino.Contracts：Race 玩家、Bot、好友、锦标赛玩家，均继承同一个 PlayerProfileData 基类。Bot 和真人共用同一张画像契约——对局/排行榜/锦标赛里的「玩家」在数据模型层无法区分，客户端消息直接从缓存取 bot 画像。这与 Dice Dreams 抓包里「排行榜 bot/FB 头像池」互为印证：SuperPlay 的对手生态是真人+bot 混池，契约层一开始就为此设计。

证据（bot 契约坐标）

  • 四画像：RacePlayerData（type[18458]）、BotProfileData（type[18459]）、FriendProfileData（type[18460]）、TournamentPlayerData（type[18462]），均继承 PlayerProfileData（type[18461]，字段 PlayerInfo/FacebookId/Level/JoinDate/PlayerStats，来源: dump_structures.txt:46914-46932）

  • 前作互证：Dice Dreams 真机抓包战报（排行榜 bot/FB 头像池）

五、工程栈盘点：第三方与开源库

栈的画像一句话：异步用 UniTask、事件用 MessagePipe、装配用 VContainer、动画 Animancer+spine 双轨、调试面板内置 SRDebugger——2025-2026 年 Unity 休闲游戏的标准现代栈，没有自研框架倾向，第三方选型全走社区主流。唯一的自研基建是 SuperHTTP（网络）和 BlueGraph（行为图，§六）。值得注意 Braze 并未在程序集清单中出现——观测栈实为 Mixpanel + Firebase + AppsFlyer + Embrace 四件。

六、配置与模板系统：四通道配置 + 可视化行为图

6.1 四族配置，两条同步路径

启动配置同步走 GCX WS 通道，一次握手带四族配置请求：MTX（变现配置，25 个缓存哈希做增量同步——客户端报本地缓存哈希，服务端只回有变化的活动配置）、PCX（第二配置通道，单哈希）、DCX（数值/服务端配置）与 LCX（本地化）不走 WS，走 CDN 直拉。客户端侧「baked / cached / live」三层配置回退——打进包里的兜底配置、上次会话缓存、本次拉取，弱网也能进游戏。客户端侧对应四个缓存加载器；配置接线是 40 个适配器阵列，每个数据域一个适配器把原始配置翻译成领域对象。

证据（配置通道坐标）

  • MTX：MTX_RequestMessage payload 含 CacheHashes（25 个 event-type-id→md5 条目） + ClanId / IncludedEventTypes / DeepLinkKey / CampaignsPreviewDate / IncludeDA / DARevision（来源: protocol-message-inventory.json:55-61；25 个缓存键含 remote-config 与 offer 块）；PCX 单 CacheHash

  • DCX/LCX CDN：https://prod-assets-cdn.domino-dreams.com/prod/server/gcx/dcx/configurations 与 .../gcx/lcx/translations（来源: capture/domino_new_account.mitm discovery 注册表 id=18/17）

  • 三层回退的埋点证词：baked dcx loaded / baked llx loaded / cached lcx loaded / cached mtx loaded / live pcx loaded / live mtx loaded / load live dcx error 等（来源: capture/domino_new_account.mitm 事件名清单）

  • 适配器：40 个 *DCXAdaptor（其中 23 个以 DataDCXAdaptor 后缀命名；样例 AchievementsDataDCXAdaptor / AdUnitsDataDCXAdaptor / EconomyIndexMappingDCXAdaptor / EconomyWRParametersDCXAdaptor / CoinProgressionDataDCXAdaptor / FeatureUnlockDCXAdaptor…，grep SuperPlay.Domino.Game.*DCXAdaptor$ 计数 = 40）；缓存元数据 DCXCacheInfo / LCXCacheInfo / DCXCCCacheInfo（dump_structures.txt:23213-23217）

6.2 BlueGraph：运营活动的可视化编程运行时

Domino.TemplatesBehavior.Runtime.dll（887 类型）内嵌一整套 BlueGraph 节点图框架（开源可视化编程框架：编辑器里画节点图、运行时按图执行）。节点库即运营能力清单：开箱、写活动状态、IAP 选档逻辑（是图节点！）、播音频……样例见证据块。

这套系统的完整含义：行为图运行时不直接依赖任何业务系统，全部通过接口端口取能力（八个 Provider 端口：分析/购买/奖励/玩家状态/弹窗位置/事务/触发器/提示）——图可以由服务端/编辑器任意组合，客户端只保证端口实现齐全。MTX 的活动/offer/弹窗逻辑在编辑器里画图生成，随 MTX 配置下发执行。新增一个运营活动不需要发版——Templates（489 类型，UI 模板组件）+ TemplatesBehavior（887 类型，图执行引擎）+ MTX delta 同步构成完整 LiveOps 内容管线。具体模板样例：补偿模板、徽章组件、开箱动画、贴纸动画。

证据（BlueGraph 坐标）

  • 框架：BlueGraph.Graph / BlueGraph.Node / BlueGraph.Port / PortDirection / PortCapacity / Connection / Comment / Group（来源: dump_structures.txt:54770 节 type[12281]-[12298]）

  • 节点样例：UnpackChest（开箱）、ShowTextResourceGroupTooltip（文案提示）、WriteEventStatePixelPath / WriteStateBagGeneric（写活动状态）、IAP.IsDtcSelected / IAP.SelectDtc（IAP 选档逻辑是图节点）、Action.PlayAudio（来源: dump_structures.txt:12252-12262）

七、工程质量评估

栈的年龄：全新。 Unity 6000.4.12f1（Unity 6 是 2025 年后的最新大版本线）；IL2CPP metadata v39 新到 Il2CppDumper 直接崩溃，本次靠 REA 直拆 metadata 才解开。targetSdk 36。版本 1.64.1.0——版本号已迭代到第 64 个 minor 版本，发布节奏极快。

规模：24,673 类型 / 149,003 方法，自有代码合计 10,563 类型。单一程序集最大 2,752 类型（Domino.Game），但内部按子命名空间继续切分——巨型程序集内部仍有模块纪律。

工程化程度（白话）：

  • 状态机驱动：核心流程全部状态机化（38 类 Game.States + GameManager.States）

  • 移动端生命周期一等公民：socket 休眠协议 + iOS Live Activities / Android ForegroundService——对局状态推送到锁屏

  • GC 治理：垃圾回收是被主动监控的指标（接口 + 埋点事件）

  • 埋点密度：新账号 11 分钟会话捕获 66 个唯一事件名、406 处 /track 调用串、10 个上报流；会话记录口径开局 2 分钟约 125 条埋点。事件覆盖资源进出、奖励链路逐步、配置加载、情绪点。资源进出全量埋点意味着经济系统可以被逐玩家逐局审计——这是做数值平衡的基建

  • 弹性设计：配置三层回退（baked/cached/live）、IAP 交易对账协议（掉单必补）、登录失败补偿查询

安全姿态：TLS 证书 pin 双向部署 + Play Integrity 全量接入 + IAP 走专用清算服务 DTC。抓包实战印证：本次 MITM 在 TLS 层直接失败；三层 hook 全部命中返回 true 但 TLS 握手仍持续失败——pin 的实际裁决门在 Mono native TLS 层（native = 编译后的机器码层，managed = 可读的 C# 代码层；hook 工具只能拦 C# 层，够不着机器码层），managed 层 hook 不可达，防护强度高于表面；最终以放行直连 + frida 应用层捕获明文帧破局。运行环境检测（Play Integrity）叠加上述 pin，实际门槛很高。

短板：协议明文 JSON 无混淆，中间人可读可写（本次 TX 侧即明文捕获）；pin 的绕过成本对一个有 frida 经验的团队是一天级。SuperPlay 的安全投资集中在设备完整性（Play Integrity）而非协议保密性——正确的取舍：作弊的经济学在假设备+假收据，不在协议逆向。

证据（工程质量坐标）

  • 引擎版本：libil2cpp.so 内嵌路径字符串 C:/Program Files/Unity/Hub/Editor/6000.4.12f1/... 与 frida-unpin.log [*] unity 6000.4.12f1；metadata v39 崩溃实录 ERROR: Metadata file supplied is not a supported version[39]（dump-il2cpp.log:5）；targetSdk 36；版本 1.64.1.0（protocol-message-inventory.json:7）

八、与 Dice Dreams 同门对比：一次网络架构换代

同为 SuperPlay 出品，两代产品的抓包证据并排看，演进脉络清晰：

维度 Dice Dreams（前作） Domino Dreams（本作） 证据
服务发现 /api/discovery/endpoints 返回 REST API 地图 同名机制，返回混合注册表（6 wss + 3 https + CDN + pin） 前作抓包战报; discovery JSON
游戏实时协议 WS（MessagePack 变体） 六服务全 WS，wire 明文 JSON 前作抓包战报; protocol inventory:4
配置同步 REST hash 增量（/api/v2/dcx?Hash=，无变化 45B） WS delta（MTX_RequestMessage CacheHashes 25 键）+ DCX/LCX 走 CDN 前作抓包战报; inventory:55-57
配置家族 GCX/ACX/MTX/DCX/CCX/LCX/DRX 七族 MTX/PCX（WS）+ DCX/LCX（CDN）四族，族数收窄 前作抓包战报; §6.1

静态资源 — DCX/LCX/翻译全上 CloudFront CDN capture discovery id=17,18

三条结构性判断：

  1. 从 REST 轮询到 WS 长连接。前作所有业务走 REST 短连接（含配置、交易、排行榜），本作把有状态、高频、服务端可主动推的业务全部迁到 WS 六通道，按业务域分服务（game/dtc/social/race/tournaments/gcx 各自独立部署、独立扩缩容）。这是典型的微服务后端在前端的投影。

  2. 配置分发去应用化。前作配置走应用 API；本作把 DCX/LCX 这类无状态只读大文件下沉到 CDN，应用 API 只留 delta 协商——带宽成本和延迟都降一级。

  3. 协议反而更「裸」。前作 WS 用 MessagePack 变体（二进制），本作用明文 JSON。序列化人类可读、直接用 Newtonsoft、调试零工具——在已有 TLS pin + Play Integrity 防线的前提下，协议混淆的边际收益被放弃了。工程效率优先。

（前作证据来源：Dice Dreams 真机抓包战报；本作证据来源：本作协议清单全文与 discovery 响应抓包。）

九、可借鉴的工程实践（站在长线休闲游戏团队的视角）

按可迁移性排序，每条注明成本档位：

  1. 配置三层回退（baked/cached/live）+ delta 同步——成本低，收益极大。包内打一份兜底配置，本地缓存上次会话版本，启动时只拉哈希不同的部分。数值表、活动参数照此改造后，弱网环境的玩家进游戏不再被配置拉取卡死，服务端带宽省一个数量级。配置事件成对埋 loaded/error 便于监控配置通道健康。

  2. 资源进出全量埋点——成本低。coins in/out、stars in/out 每笔带来源/去向。变现与留存的调优都要求先能回答「资源从哪来、到哪去」，经济流水审计是调奖励节奏的前提；SuperPlay 连 reward sequence step tapped to skip 都埋，说明他们用埋点直接驱动奖励节奏调优。

  3. SocketComponent 模式：多服务长连接 + 统一基类——中成本。若要做实时性更强的玩法（实时对战），按业务域拆 WS 服务、共享一个含登录/批处理/休眠/风控判定的基类，比单连接多路复用好维护；休眠协议省电对中低端设备是留存问题不是优化问题。

  4. 契约层先行（Contracts 程序集）——中成本。接口端口与实现分离，bot 与真人共用画像契约。若要做 bot 混池（对手生态的常见做法），从第一天就把 PlayerProfileData 设计成统一契约，bot 只是其中一个实现，后期不用返工。

  5. 客户端模拟器作为一等公民——中成本。Domino.Simulation 六个模拟器（含概率模拟）说明 SuperPlay 的数值验证不靠感觉。自己的关键数值值得配一个可跑对拍的模拟器——「数值必须跑模拟」这条策略在他们那里是工程化的。

  6. 行为图 LiveOps 管线（BlueGraph 模式）——高成本，长期收益最大。活动逻辑画图生成、随配置下发、不占发版。小团队完整复刻不现实，但可以取其神：活动配置里嵌行为描述（哪怕只是简单的触发条件+奖励 JSON），客户端一个通用执行器解释执行，先把「新活动不发版」做到 60 分。

  7. 安全投资集中在设备完整性而非协议保密——低成本正确取舍。TLS pin（服务端下发指纹可轮换）+ Play Integrity + IAP 服务端权威清算（掉单必补的对账协议），不搞协议加密混淆。自己的 IAP 对账协议（GetUnconsumedTransactions 形态）值得尽早补齐。

一句话总结：Domino Dreams 的架构没有炫技，每一处自研（SuperHTTP、BlueGraph）都服务于同一个目标——让 LiveOps 内容的生产和分发不依赖客户端发版。这是超休闲长线运营的架构终局形态，也是长线产品从「一次性设计」走向「持续调优」最值得对齐的方向。
